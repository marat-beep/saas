# Производительность: размеры ассетов и данных (PROP-11)

Оценка объёмов критичных клиентских файлов (светлая статика, без сборки). Замеры — `gzip -9`.

| Файл | raw | gzip | Отдаётся клиенту |
|---|---|---|---|
| `assets/js/catalog.js` | 129.2 КБ | **31.0 КБ** | да (каталог 100 модулей) |
| `assets/css/app.css` | 32.8 КБ | 8.3 КБ | да |
| `assets/js/shell.js` | 23.2 КБ | 7.6 КБ | да |
| `assets/js/nav.js` | 13.9 КБ | 4.7 КБ | да |
| `index.html` | 36.5 КБ | 9.9 КБ | да |
| `tools/modules-analysis.js` | 59.2 КБ | 15.8 КБ | **нет** (build-time) |
| `tools/proposals.js` | 20.3 КБ | 6.7 КБ | **нет** (build-time) |

## Решение (PROP-11)

- **`catalog.js` (клиентский) остаётся единым файлом.** 31 КБ gzip на 100 модулей — приемлемо для статического сервиса; сюда же зашиты `quick`, `connects`, `statuses`. Вынос данных в отдельный JSON с ленивой загрузкой усложнил бы загрузку (доп. запрос, асинхронность, риск рассинхрона `CATALOG_V`) без заметной выгоды на текущем объёме.
- **`modules-analysis.js` и `proposals.js` (≈76 КБ raw) не отдаются клиенту** — используются только генераторами (`tools/gen-modules-page.js`, `tools/gen-roadmap.js`) на этапе сборки дашборда. Их объём на клиент не влияет.
- Триггер для пересмотра: рост `catalog.js` > ~200 КБ raw (или модулей > 150). Тогда — вынос описаний модулей в `assets/data/modules.json` с загрузкой по требованию и версионированием (`CATALOG_V`).

Источник: `tools/gen-modules-page.js` (панель «Зрелость модулей»), замеры `zlib.gzipSync(level 9)`.
