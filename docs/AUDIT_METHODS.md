# Методики оценки (3DMP Service · аудит)

Версия 1.0. Определяет шкалы, веса, формулы скоринга и правила приоритизации/формирования волн.

## 1. Шкала критерия (0–4)
| Балл | Значение |
|---|---|
| 0 | отсутствует |
| 1 | критично неполно |
| 2 | частично |
| 3 | соответствует |
| 4 | превосходит (эталон) |

## 2. Веса областей (A–K)
A12 B15 C15 D15 E10 F12 G6 H5 I5 J3 K2 (сумма 100). Порог RAG: 🟢 ≥85, 🟡 70–84, 🔴 <70.

## 3. Скоринг находок
- Severity (вес): Blocker=4, Critical=3, Major=2, Minor=1, Info=0.
- Impact ∈ {1 — локально, 2 — контур, 3 — сквозной/ценность/риск}.
- Effort ∈ {1,2,3,5,8} (условные пункты).
- **Приоритет:** `P = round(Impact × SeverityWeight × AreaWeight / Effort)`.
- Классы: **P0 ≥ 60**, **P1 35–59**, **P2 18–34**, **P3 < 18**.

## 4. Балл области и итог
```
deduction(sev) = { Blocker:4, Critical:2, Major:1, Minor:0.3, Info:0 }
areaScore = clamp(4 - Σ deduction, 0, 4)
areaPct   = areaScore / 4 * 100
overall%  = Σ(areaScore/4 × weight) / Σweight × 100
```
Все находки со `status ∈ {done, wontfix}` исключаются из расчёта.

## 5. Формирование волн
1. Отсортировать элементы плана по приоритету (P убыв.), внутри — по зависимостям категорий: `data(0) → backend(1) → ui(2) → docs(3)`.
2. Упаковать в волны по вместимости спринта (по умолчанию **20 условных пунктов** либо ≤ N часов); связанные элементы не разрывать.
3. Каждый элемент: DoD, артефакты, владелец, оценка, статус.
4. Волне присвоить версию `v4.<n>` в порядке приоритета.

## 6. Методы по уровням
- **L0 статик:** карта файлов/версий, синтаксис, дубли, мёртвый код, устаревшие `?v`, TODO.
- **L1 БД:** smoke/ext/wave/перегрузки/кодировка; идемпотентность миграций, ссылочная целостность, дубли.
- **L2 трассировка:** `catalog.js` ↔ `apps/<id>` ↔ RPC-вызовы ↔ UI; сироты и «мёртвые» функции.
- **L3 сценарии:** золотые/негативные/краевые; роли; мобильный/офлайн. Фиксация шагов и результата.
- **L4 применимость:** интервью, наблюдение, SUS (≥68 — цель), task-success/time-on-task, пилот.

## 7. Метрики тренда (в `audit/state.json`)
- overall% и RAG по прогонам; число находок по severity; покрытие сценариями; доля модулей с shell/caps/report; p95 RPC; кодировка («?»=0); перегрузки (=0).

## 8. Правила доказательности
Каждая находка обязана содержать `evidence` (путь:строка либо команда/артефакт) и `method`. Без доказательства находка не принимается.

## 9. Закрытие находки (DoD)
Исправление + регрессионный тест + повторный прогон проверки зелёный + обновление доков + коммит. Только затем `status: done` → после повторного авто-прогона `verifying` → `closed`.
