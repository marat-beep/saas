# MODULE_STANDARD — стандарт модуля 3DMP Service

Назначение: единый каркас и правила, чтобы все модули были однородными, связными и боевыми.
Прототипы `eco/` — **только источник идей и сценариев**. Их **не переносим как есть**; модуль проектируем и реализуем по этому стандарту.

## 1. Принципы
- **Один источник истины** — `assets/js/catalog.js`: `id, icon, title, desc, group, audience, purpose, features, connects, in_, out, roles`.
  Меню (nav), хаб, пульт, гид и экран «Модули» строятся из каталога. Хардкод списков запрещён.
- **Данные только через RPC** Supabase (SECURITY DEFINER). Клиент не ходит в таблицы напрямую.
- **Изоляция по tenant** во всех выборках (`app_my_tenant(p_token)`), роли — `app_production_allowed`/`app_session_user`.
- **Связность обязательна:** у модуля есть вход и результат; связи (`connects`) реально работают (переходы/данные), а не только описаны.
- **Единый UI:** используются общие классы `app.css` (`topbar`, `wrap`, `hero`, `card`, `field`, `btn`, `msg`, `note`), без локальных «дизайнов с нуля».

## 2. Каркас приложения `apps/<id>/`
```
apps/<id>/
  index.html   — разметка: topbar (who/logout), hero, экраны/карточки, поля, таблицы
  <id>.js      — логика: guard → загрузка RPC → рендер → действия
```
Порядок подключения скриптов (пример):
```
config.js → supabase-client.js → ui.js → status.js (если нужно) → auth.js → router.js (если экраны)
→ notify.js → catalog.js (если нужен каталог) → nav.js → <id>.js → realtime.js
```
- Версии ассетов поднимаются (`?v=N`) при изменениях.
- `nav.js` сам подтягивает каталог; добавлять `catalog.js` на страницу нужно только для рендера модулей/гида.
- Guard: `window.Auth.guard('../auth/index.html')` + проверка роли; гость — только если модуль `guest:true`.

## 3. Конвенции БД/RPC (миграции)
- Таблица: `app_<сущность>` с `id uuid default gen_random_uuid()`, `tenant_id uuid references tenants(id)`, `created_at timestamptz default now()`.
- RLS включён: `alter table ... enable row level security;` (доступ через SECURITY DEFINER RPC).
- Имена функций: `app_<сущность>_list`, `app_<сущность>_get`, `app_<сущность>_save`/`_create`, `app_<сущность>_<действие>`.
- Мутации возвращают `table(ok boolean, message text)`; создание — `table(id uuid, number text)`.
- Каждый RPC — `security definer set search_path = public`, проверка роли/тенанта, аккуратные сообщения об ошибках на русском.
- Миграции — только `supabase/migrations/NNNN_*.sql`, идемпотентно; после — пересобрать `apply_all.sql`.
- Смена типа возврата функции — сначала `drop function if exists ...;` (иначе повторный `apply_all` падает на `42P13`).
- **Обязательно:** в plpgsql-функциях, возвращающих таблицу с колонкой `id` (и вообще при `RETURNS TABLE(...)`), первой строкой тела (после `as $$`, перед `declare`/`begin`) указывать прагму
  `#variable_conflict use_column`
  иначе `RETURNING id` / `WHERE id = ...` падают с `42702 column reference "id" is ambiguous` (OUT-параметр конфликтует с колонкой). Проверено на всех 385 функциях (`app_smoke_test`).

## 4. Поведение модуля (обязательный минимум)
- Уведомления: `app_notif_roles_t` / `app_notif_send` на значимые события.
- Журнал: `window.Auth.log(...)` на действия пользователя.
- Заявки: если модуль порождает работу — уметь создать `app_orders` (source = id модуля).
- Экспорт: по возможности выгрузка через `assets/js/export.js`.
- Демо-данные: наполнение для тенанта A, идемпотентно.
- Проверка: баланс скобок JS, соответствие `id` HTML/JS, валидность путей, `?v=N`.

## 5. Чек-лист нового/переработанного модуля
- [ ] Запись в `catalog.js` (группа, аудитория, purpose/features/connects, in_/out).
- [ ] `apps/<id>/` по каркасу, единый UI.
- [ ] Миграция + RPC (list/get/save), tenant + роли, RLS.
- [ ] Связи с другими модулями работают (данные/переходы).
- [ ] Уведомления + журнал; экспорт (если применимо).
- [ ] Демо-данные; проверка целостности; коммит; FTP; записи в STATUS/NOTES.

## 6. Сверка с ТЗ (augmentation) — обязательный шаг при обновлении модуля
> Типовая структура и порядок правок для переноса на другие модули — `MODULE_BLUEPRINT.md`.

Когда по модулю есть ТЗ (txt/html/док), работаем так:
1. **Прочитать ТЗ целиком** и составить гап-анализ: «что уже есть в модуле / чего нет / что доработать».
2. **Дополнять существующий модуль, а не создавать дубль.** Новые поля/таблицы/RPC/экраны добавляются к текущему `apps/<id>`, старые данные и связи сохраняются.
3. **Не терять пункты ТЗ:** каждому пункту соответствует поле, таблица, RPC, блок UI, KPI или связь. Ведём чек-лист покрытия.
4. **Архитектурная адаптация.** ТЗ может описывать микросервисы, Kafka, TimescaleDB, Redis, S3, OAuth, native-mobile — переносим на наш стек:
   - микросервисы → модули каталога + RPC;
   - шина событий/очередь → `app_integrations`/`app_integration_log` (очередь + ретраи);
   - TimescaleDB → обычная таблица метрик (`app_iiot_metrics`), при росте — партиционирование;
   - native mobile → PWA (`sw.js`, `offline-queue.js`);
   - внешние порталы (дилер/поставщик) → отдельная роль + портал по образцу `apps/supplier`.
5. **План фиксировать в `BACKLOG.md`** (ID, артефакты, DoD) до реализации; после — отметки в `PLAN_WAVES.md`, `STATUS/NOTES/PROMPTS`.
6. **DoD сверки:** все пункты ТЗ либо реализованы, либо явно вынесены в бэклог с причиной.

## 7. Проверенные приёмы и «грабли» (накоплено по волнам W1–W6)
**Миграции и plpgsql**
- Первой строкой тела функции (после `as $$`) — `#variable_conflict use_column`.
- Локальные переменные **не называть как OUT-колонки** (иначе в `SELECT` они затеняются): `v_ucl`, `v_cp`, `newretry`, `iid`, `l_id` и т. п.
- Смена сигнатуры/типа возврата — сначала `drop function if exists <точная сигнатура>;` затем `create or replace`.
- **Не присваивать поля record**: `select a, b into rec.a, rec.b` → ошибка `55000`. Использовать скаляры: `select a, b into l_a, l_b`.
- Временная таблица из INSERT: `with ins as (insert ... returning id) select id from ins` (не `create table as insert`).
- Демо с фиксированным номером + последовательность: после вставки `select setval('..._seq', greatest(max(суффикс), 1));`, иначе следующий `nextval` даст дубль.
- Идемпотентность демо/КБ: `insert ... select ... where not exists (...)`.
- Для больших текстов — `left(text, N)`; при обновлении nullable jsonb/токена пустое значение трактуем как «не менять» (`coalesce`/`case when trim(...)=''`).
- В конце миграции — `grant execute on function ... to anon, authenticated;` для каждого RPC.
**Доступ, данные, уведомления**
- Нетиповые модули: строки в `app_role_permissions` (`tenant_id null`) + проверка `app_can(token,'<модуль>','view'/'edit')`; admin/owner — неявно.
- `app_can` для неизвестного модуля: просмотр разрешён, правка — нет — задавайте матрицу явно.
- Уведомления — `app_notif_roles_t(tenant, roles[], title, body, url)`; роль-получатель должна существовать (иначе тихо никого не уведомит).
**Realtime / офлайн / интеграции**
- Realtime — best-effort: подписка `AppRealtime.watch` + **обязательный фолбэк-опрос** (собственный вход = anon, RLS может блокировать события). Публикация таблицы — guarded `do $$ ... exception when duplicate_object ... $$`.
- Офлайн-очередь — `AppOffline.add({rpc, args, label})`; `flush()` по `online`; клиентский id + журнал `app_offline_sync`.
- Внешние системы — через очередь `enqueue`/`process` (статусы `pending→error→failed`, `retry_count`, `next_retry_at`), ручной повтор; реальная отправка — серверный воркер/Edge (образец `backend-example/`, allow-list/токен).
**UI/ассеты**
- Графики — SVG-строкой без внешних зависимостей (образец: SPC в `apps/qc`).
- Многoэкранные модули — `AppRouter.create` (screens), KPI — `cell()`, табы — `.tabs2`, формы — `AppUI.formDialog`, модалки с контентом — `ui.dialog({html,onOpen})`, вложения — `files.js`.
- Поднимать `?v=N` у **изменённых** ассетов на **всех** страницах; `CATALOG_V` — в `nav.js` и `shell.js`; версии `catalog`/`nav`/`shell` синхронизировать.
**Процесс**
- `apply_all.sql`: блок строго между маркерами `-- >>>>>>>>>> NNNN_name.sql` / `-- <<<<<<<<<< NNNN_name.sql`; при правке миграции — пересобрать её блок (не плодить дубли).
- Применение SQL: Management API **только UTF-8** — `@{query=$sql} | ConvertTo-Json` + `[System.Text.Encoding]::UTF8.GetBytes(json)`, `ContentType 'application/json; charset=utf-8'`.
- Проверки перед коммитом: `node --check` для изменённых JS; смоук `app_smoke_test` (10/10) и `app_smoke_test_ext` (14/14); функц. тест RPC с **очисткой тестовых данных**.
- Деструктивные/мутирующие git-команды и push — только по явной просьбе; FTP-деплой — по регламенту.

## 8. Анти-паттерны (чего не делаем — как в прототипах)
- Хардкод данных в JS без БД; «красиво, но не связано».
- Свои названия/структуры у каждого экрана; несогласованный UI.
- Прямые запросы к таблицам из клиента; отсутствие tenant/role-проверок.
- Списки модулей, продублированные в разных файлах.
- Перенос прототипа «как есть» без переработки под стандарт.
- Создание второго модуля-дубля вместо дополнения существующего по ТЗ.
